# 业务逻辑审查

对已生成的代码进行业务逻辑层面的深度审查，聚焦数据流转、边界处理、事务完整性，输出结构化审查报告。

## 定位

本 skill 是代码生成后的**质量关卡**——确保"做对了"，而非仅"做完了"。

```
代码生成  →  review-business-logic  →  修复/通过
  (实现)       (业务逻辑审查)         (决策)
```

## 审查维度

| 维度 | 关注点 | 优先级 |
|------|--------|--------|
| **数据完整性** | 字段映射是否遗漏？List/嵌套结构是否正确展开？溯源信息是否传递？ | P0 |
| **事务边界** | 数据写入方法是否加 `@Transactional`？多表操作是否在同一事务？ | P0 |
| **异常处理** | 是否吞掉异常？业务异常是否用 `TaurusException`？空指针风险？ | P0 |
| **业务规则** | 增量跳过逻辑是否正确？版本管理是否闭环？fileTag 分流是否覆盖全部 case？ | P1 |
| **性能隐患** | N+1 查询？循环内数据库操作？大对象未分页？ | P1 |
| **代码规范** | 是否用 `javax.*`？日志是否用 SLF4J？硬编码密钥？ | P2 |

## 审查流程

### 步骤 0：检查目录

检查 `docs/03.业务审查结果/` 目录是否存在，若不存在则创建。

### 步骤 1：确定审查范围

从用户输入或代码变更中提取：
- **目标文件**：哪些 Controller/Service/Mapper 需要审查？
- **关联模块**：涉及哪些业务模块（项目/文件/尽调/文档定位）？
- **变更类型**：新增功能 / 修改逻辑 / 修复 Bug？

若用户未明确，默认审查最近修改的 Service 层文件（业务逻辑核心）。

### 步骤 2：静态分析代码

按以下顺序逐层审查：

#### 2.1 Controller 层
- [ ] 参数校验：是否使用 `@Valid` + Jakarta Validation？
- [ ] 响应封装：是否统一返回 `Result<T>`？
- [ ] 路由规范：是否 POST + 明确路径？
- [ ] 职责边界：是否仅做参数转发，无业务逻辑？

#### 2.2 Service 层（重点）
- [ ] 事务控制：数据写入方法是否标注 `@Transactional(rollbackFor = Exception.class)`？
- [ ] 依赖注入：是否使用 `@RequiredArgsConstructor` + final 字段？
- [ ] 异常处理：业务失败是否抛 `TaurusException` 或 `AssertUtils` 校验？
- [ ] 数据流转：DTO → Entity → VO 转换是否完整？有无字段遗漏？
- [ **List/嵌套结构**：批量数据是否正确遍历？是否仅插入第一条？（历史高频问题）
- [ ] 溯源传递：`trace_info` 是否正确组装并持久化？
- [ ] 增量逻辑：版本号判断、文件已处理标记是否闭环？

#### 2.3 Mapper 层
- [ ] 查询安全：是否使用 `LambdaQueryWrapper`（类型安全）？
- [ ] 批量操作：是否避免 N+1 查询？是否用批量插入？
- [ ] SQL 注入：动态 SQL 是否使用 `#{}` 而非 `${}`？

### 步骤 3：追踪关键链路

针对核心业务场景，从 Controller 入口追踪至数据库：

```
Controller 接收请求
  ↓ 参数校验
Service 编排逻辑
  ↓ 事务开启
  ├─ 查询现有数据（版本判断/增量跳过）
  ├─ 外部调用（MinerU/LLM/MinIO）
  ├─ 数据转换（DTO → Entity）
  ├─ 批量写入（字段/溯源）
  └─ 事务提交
```

**重点验证**：
1. **分流逻辑**：PDF/Excel/Vision 多路分支是否覆盖所有 fileTag？
2. **溯源闭环**：提取的字段是否关联 `trace_info`（来源文件、坐标、置信度）？
3. **版本管理**：新建版本时旧版本是否保留？增量提取是否跳过已处理文件？

### 步骤 4：识别边界风险

检查以下场景是否处理：
- 空数据：解析结果为空时是否优雅降级？
- 超大文件：Excel 多 Sheet/万行数据是否分页处理？
- 并发写入：同一项目同时生成报告是否冲突？
- 外部失败：MinerU/LLM 超时是否重试或标记 failed？

## 注意事项

- **聚焦业务逻辑**：不审查代码风格、命名规范（交给 IDE/Checkstyle），专注"逻辑对不对"
- **证据驱动**：每个问题必须标注文件路径 + 行号 + 代码片段，不空泛点评
- **分级处理**：P0 必须修复（数据错误/事务缺失/异常吞掉），P1 建议修复，P2 可选
- **关联历史**：优先复核记忆中的历史问题（如 List 映射、MinIO URL 拼接）
- **不替用户决定**：边界场景处理方式记入"优化建议"，由主公决策
