# 需求讨论与文档生成

引导用户深入讨论复杂功能需求，输出结构化需求说明书，为 `create-plan` 开发计划提供清晰的输入。

## 定位

本 skill 是 `create-plan` 的**上游**——先理清"要做什么"，`create-plan` 再解决"怎么做"。

```
create-requirement          create-plan
  (需求说明书)      →       (开发计划)
    要做什么                   怎么做
```

## 需求文档结构

> **原则**：需求文档聚焦"做什么、为谁做、做到什么程度"，不涉及技术实现细节。

生成文件路径：`docs/01.需求编写/{YYYYMMDD}_{功能名称}-requirement.md`

```markdown
# {功能名称} 需求说明书

> 版本：v1.0 | 日期：{日期} | 作者：{作者}

## 一、功能概述
// 一句话说明功能是什么，解决什么问题

## 二、用户场景
// 谁、在什么情况下、要做什么、期望什么结果

| 场景 | 角色 | 前置条件 | 操作 | 期望结果 |
|------|------|----------|------|----------|

## 三、功能需求
// 核心功能点，按优先级排列

### 3.1 {功能点1}（P0）
- **描述**：...
- **输入**：...
- **输出**：...
- **业务规则**：...

### 3.2 {功能点2}（P1）
...

## 四、非功能需求
// 性能、安全、可用性等

| 维度 | 要求 |
|------|------|
| 性能 | ... |
| 安全 | ... |
| 兼容性 | ... |

## 五、约束与依赖

### 5.1 前置依赖
// 依赖哪些已有模块/接口/数据表

### 5.2 边界条件
// 数据量上限、并发上限、异常场景等

## 六、验收标准
// 可验证的完成标准

- [ ] 场景1：... → 结果...
- [ ] 场景2：... → 结果...
- [ ] 异常1：... → 处理...

## 七、待澄清问题（可选）
// 记录当前无法确定、需后续确认的点

---
> 编写：{作者} | 日期：{日期}
```

## 执行步骤

### 步骤 0：检查目录

检查 `docs/01.需求编写/` 目录是否存在，若不存在则创建。

### 步骤 1：确认功能名称和范围

从用户输入提取：
- **功能名称**：用于文件命名和标题
- **一句话概述**：用户想解决什么问题
- **范围边界**：做什么、不做什么

若用户描述模糊，先通过提问明确以上三点，再进入下一步。

### 步骤 2：讨论用户场景

按以下维度与用户逐一确认：

1. **谁用**：哪些角色会使用此功能？
2. **何时用**：在什么业务流程/场景下触发？
3. **怎么用**：操作步骤是什么？
4. **预期结果**：操作后期望看到什么？

对每个场景，以表格形式整理。

### 步骤 3：梳理功能需求

针对每个场景，拆解为具体功能点：

1. 列出所有功能点，标注优先级（P0 必须 / P1 重要 / P2 锦上添花）
2. 明确每个功能点的输入、输出、业务规则
3. 区分"核心路径"和"异常路径"

### 步骤 4：确认非功能需求

引导用户考虑：

- **性能**：响应时间要求？并发量？
- **安全**：权限控制？数据脱敏？
- **数据量**：预期数据规模？
- **兼容性**：需兼容的浏览器/环境？

不强制逐项填写，只记录用户关心的。

### 步骤 5：梳理约束与依赖

- 依赖哪些已有模块/数据表/外部接口？
- 有哪些硬性约束（技术栈、规范、第三方限制）？
- 边界条件是什么（最大数据量、极端情况）？

### 步骤 6：制定验收标准

将功能需求转化为可验证的 checklist：
- 正常场景验收
- 异常场景验收
- 每个条目可独立验证

### 步骤 7：创建文档

按模板生成 `docs/01.需求编写/{YYYYMMDD}_{功能名称}-requirement.md`，填充所有已确认内容。

待澄清问题单独记录在第七节，不强行编造答案。

## 注意事项

- **聚焦"做什么"，不讨论"怎么做"**：技术方案、API 设计、数据库设计留给 `create-plan`
- **宁可留白，不编造**：用户不确定的点记入"待澄清问题"，别替用户做决定
- **场景驱动**：以用户场景为线索串联需求，避免干瘪的功能列表
- **优先级明确**：P0/P1/P2 必须标注，帮助后续 `create-plan` 排期
- **文档精简**：每个功能点控制在 5-10 行，避免长篇大论
- **与 create-plan 衔接**：需求说明书的"功能概述"可直接作为开发计划的"需求概述"输入
